## Context

Эндпоинт `/room/{roomId}/board` используется для long-polling получения актуального состояния доски. Сейчас он не проверяет, кто именно делает запрос. Клиент уже передаёт логин пользователя в DOM через `<span id="login">` в [`game.html`](src/main/resources/templates/game.html:41), а [`script.js`](src/main/resources/static/js/script.js:73) формирует запрос без какого-либо заголовка аутентификации.

## Goals / Non-Goals

**Goals:**
- Клиент добавляет заголовок `Authorization: Basic <base64(login)>` при запросе к `/room/{roomId}/board`.
- Сервер читает и декодирует заголовок `Authorization` и проверяет, что пользователь с таким логином существует в репозитории.
- Невалидный/отсутствующий заголовок приводит к ответу `401 Unauthorized`.

**Non-Goals:**
- Не вводится полноценная Spring Security и пароли — передаётся только логин.
- Не меняется поведение `/game` и других эндпоинтов.
- Не вводится сессионная проверка (`uid`) для этого запроса.

## Decisions

**Decision 1: Передавать логин через Basic Auth в заголовке `Authorization`.**
Формат `Basic <base64(login)>`. Логин уже доступен на клиенте через `login.textContent`. Такой подход минимально изменяет существующую модель аутентификации (только логин, без пароля) и позволяет серверу однозначно идентифицировать пользователя.
Альтернатива: передавать `uid` из сессии через query-param — отклонено, т.к. session id не доступен клиентскому JS напрямую, а query-param виден в истории и логах.

**Decision 2: Декодирование и валидация на сервере в `getRoomBoard()`.**
Контроллер [`RoomController.getRoomBoard()`](src/main/kotlin/ru/kiseru/checkers/controller/RoomController.kt:149) принимает заголовок `Authorization`, извлекает часть после `Basic `, декодирует из base64 и ищет пользователя по имени через `userRepository`. Если заголовок отсутствует, имеет неверный формат или пользователь не найден — выбрасывается `ResponseStatusException(HttpStatus.UNAUTHORIZED)`.
Альтернатива: отдельный фильтр/интерцептор — избыточно для одного эндпоинта.

**Decision 3: Клиент кодирует логин в base64.**
Используется `btoa()` (значение `login.textContent.trim()`). Кодирование выполняется перед каждым запросом в функции `subscribe`, чтобы всегда отправлять актуальный логин.

## Risks / Trade-offs

- [Basic Auth передаётся по незашифрованному HTTP, логин виден в открытом виде] → В проекте только логин (без пароля), что снижает чувствительность; для production рекомендуется HTTPS. В рамках данной задачи TLS вне скоупа.
- [Логин с символами вне Latin-1 ломает `btoa()`] → Использовать `encodeURIComponent` перед кодированием либо `TextEncoder`/`btoa` с корректным преобразованием UTF-8; при необходимости обработка через `unescape(encodeURIComponent(...))`.
- [Ретраи запроса без корректного заголовка приводят к бесконечному циклу] → Текущая логика `subscribe` уже обрабатывает не-200 ответы с задержкой; 401 будет обработан как обычный не-200.
